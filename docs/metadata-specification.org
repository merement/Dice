#+TITLE: Relaxed-Spin Data Metadata and Streaming Format
#+AUTHOR: Internal Draft
#+OPTIONS: toc:2

* Overview

This document specifies a backward-compatible metadata extension for relaxed-spin
data files and a related NDJSON-based message format for future stream-based
transport.

The existing relaxed-spin data format consists of numeric data records of the
form:

#+BEGIN_EXAMPLE
time spin_1 X_1 spin_2 X_2 spin_3 X_3 ...
#+END_EXAMPLE

where:

- ~time~ is a floating-point value;
- each ~spin_i~ is either ~+1~ or ~-1~;
- each ~X_i~ is a floating-point value;
- each logical node is represented in the numeric data line by the pair
  ~spin_i X_i~.

Although the file layout represents each node by a pair of values, the semantic
entity is a single relaxed spin assigned to a node. Therefore, metadata
will refer to these entities as *nodes*.

Legacy parsers (are assumed to) ignore lines beginning with ~#~. This
specification uses such comment lines to embed machine-readable metadata
without breaking existing parsers.

Machine-readable metadata is represented as newline-delimited JSON, or NDJSON,
with a comment prefix in file-based data.

* Terminology

** Node

A *node* is the semantic entity represented in a data line by one adjacent
~spin_i X_i~ pair.

For example, in the data line layout:

#+BEGIN_EXAMPLE
time spin_1 X_1 spin_2 X_2 spin_3 X_3 ...
#+END_EXAMPLE

node 1 is represented by:

#+BEGIN_EXAMPLE
spin_1 X_1
#+END_EXAMPLE

node 2 is represented by:

#+BEGIN_EXAMPLE
spin_2 X_2
#+END_EXAMPLE

and so on.

** Data record

A *data record* is a non-comment numeric line containing a time value followed by
node states.

Example:

#+BEGIN_EXAMPLE
0.000  1 0.12  -1 0.44  1 0.91
#+END_EXAMPLE

** Metadata record

A *metadata record* is a machine-readable JSON object embedded in a comment line.

In files, metadata records have the form

#+BEGIN_EXAMPLE
#@ {"type": "node", "index": 5, "name": "pass_a"}
#+END_EXAMPLE

The part after ~#@~ is a complete JSON object.

** Stream message

A *stream message* is the same JSON object transmitted directly as one NDJSON
record, without the file comment prefix.

Example:

#+BEGIN_SRC json
{"type": "node", "index": 5, "name": "pass_a"}
#+END_SRC

* File-Based Format

In files, ordinary numeric data records remain unchanged.

Example:

#+BEGIN_EXAMPLE
0.000  1 0.12  -1 0.44  1 0.91
0.100  1 0.15  -1 0.43  1 0.89
#+END_EXAMPLE

Human-readable comments begin with ~#~ and are ignored by both legacy and
enhanced parsers unless an application chooses to preserve them separately.

Example:

#+BEGIN_EXAMPLE
# This is a human-readable comment.
# Generated by run 123.
#+END_EXAMPLE

Machine-readable metadata lines begin with ~#@~ followed by a single JSON
object.

Example:

#+BEGIN_EXAMPLE
#@ {"type": "format", "name": "relaxed-spins", "version": 1}
#@ {"type": "node_indexing", "base": 1}
#@ {"type": "node", "index": 1, "name": "CTRL_1"}
#@ {"type": "node", "index": 5, "name": "pass_a"}
#@ {"type": "node", "index": 6, "name": "pass_b"}
#+END_EXAMPLE

Legacy parsers continue to ignore all lines beginning with ~#~.

Enhanced parsers interpret only lines beginning with ~#@~.

* Metadata Line Syntax

A metadata line has the form:

#+BEGIN_EXAMPLE
#@ <json-object>
#+END_EXAMPLE

where ~<json-object>~ is a complete JSON object contained on a single physical
line.

Valid example:

#+BEGIN_EXAMPLE
#@ {"type": "node", "index": 5, "name": "pass_a"}
#+END_EXAMPLE

Invalid examples:

#+BEGIN_EXAMPLE
#@ ["node", 5, "pass_a"]
#@ "node"
#@ 42
#@ {"type": "node",
#@  "index": 5,
#@  "name": "pass_a"}
#+END_EXAMPLE

The JSON value following ~#@~ should be an object. Multi-line JSON objects are
not part of the base file format.

* Ordinary Comments

Lines beginning with ~#~ but not ~#@~ are ordinary comments.

Example:

#+BEGIN_EXAMPLE
# This is a normal comment.
# TODO: check convergence.
# Generated on test backend.
#+END_EXAMPLE

Enhanced parsers should ignore these lines for purposes of machine-readable
metadata.

* General Metadata Record Structure

Every machine-readable metadata record should contain a ~type~ field.

Example:

#+BEGIN_SRC json
{"type": "node", "index": 5, "name": "pass_a"}
#+END_SRC

The ~type~ field identifies the semantic meaning of the record.

Parsers should ignore records with unknown ~type~ values unless operating in a
strict validation mode.

Example of an unknown future record:

#+BEGIN_EXAMPLE
#@ {"type": "visualization_hint", "color_by": "spin"}
#+END_EXAMPLE

A parser that does not understand ~visualization_hint~ should ignore the record
and continue processing.

* Core Metadata Types

** Format declaration

The format declaration identifies the file or stream format.

Example:

#+BEGIN_EXAMPLE
#@ {"type": "format", "name": "relaxed-spins", "version": 1}
#+END_EXAMPLE

Fields:

- ~type~: must be ~"format"~;
- ~name~: format name;
- ~version~: integer format version.

Recommended value:

#+BEGIN_SRC json
{"type": "format", "name": "relaxed-spins", "version": 1}
#+END_SRC

** Node indexing

The node indexing record defines the global base used for node indices.

Example:

#+BEGIN_EXAMPLE
#@ {"type": "node_indexing", "base": 1}
#+END_EXAMPLE

Fields:

- ~type~: must be ~"node_indexing"~;
- ~base~: integer indexing base.

Supported base values in this version are:

- ~1~ for 1-based indexing;
- ~0~ for 0-based indexing.

Example using 1-based indexing:

#+BEGIN_EXAMPLE
#@ {"type": "node_indexing", "base": 1}
#@ {"type": "node", "index": 1, "name": "CTRL_1"}
#+END_EXAMPLE

Example using 0-based indexing:

#+BEGIN_EXAMPLE
#@ {"type": "node_indexing", "base": 0}
#@ {"type": "node", "index": 0, "name": "CTRL_1"}
#+END_EXAMPLE

The meaning of ~base~ is global for the file or stream session.

The ~node_indexing~ record should appear before any record that refers to node
indices.

If no ~node_indexing~ record is present, parsers should assume:

#+BEGIN_SRC json
{"type": "node_indexing", "base": 1}
#+END_SRC

However, producers should emit an explicit ~node_indexing~ record.

Conflicting ~node_indexing~ records within the same file or stream should be
treated as an error in strict mode and as a warning in permissive mode.

For example, the following is invalid or strongly discouraged:

#+BEGIN_EXAMPLE
#@ {"type": "node_indexing", "base": 1}
#@ {"type": "node", "index": 5, "name": "pass_a"}
#@ {"type": "node_indexing", "base": 0}
#@ {"type": "node", "index": 5, "name": "other"}
#+END_EXAMPLE

** Node metadata

Node metadata assigns metadata to a node.

Example:

#+BEGIN_EXAMPLE
#@ {"type": "node", "index": 5, "name": "pass_a"}
#+END_EXAMPLE

Fields:

- ~type~: must be ~"node"~;
- ~index~: node index, interpreted according to the global ~node_indexing~ base;
- ~name~: optional string name for the node.

Additional fields may be added in the future.

Examples:

#+BEGIN_EXAMPLE
#@ {"type": "node", "index": 1, "name": "CTRL_1"}
#@ {"type": "node", "index": 5, "name": "pass_a"}
#@ {"type": "node", "index": 6, "name": "pass_b"}
#+END_EXAMPLE

Future extensions may include additional node attributes:

#+BEGIN_EXAMPLE
#@ {"type": "node", "index": 5, "name": "pass_a", "role": "diagnostic"}
#@ {"type": "node", "index": 6, "name": "pass_b", "units": "arb"}
#+END_EXAMPLE

Parsers should ignore unrecognized fields unless operating in strict validation
mode.

** Creation timestamp

A creation timestamp may be represented as:

#+BEGIN_EXAMPLE
#@ {"type": "created", "value": "2026-01-26T18:44:00Z"}
#+END_EXAMPLE

The timestamp should preferably use ISO 8601 format.

** Title

A short title may be represented as:

#+BEGIN_EXAMPLE
#@ {"type": "title", "value": "Relaxed-spin trajectory for test run 42"}
#+END_EXAMPLE

** Notes

A longer notes or description may be represented as:

#+BEGIN_EXAMPLE
#@ {"type": "notes", "value": "Simulation after thermal relaxation stage."}
#+END_EXAMPLE

* Node Indexing Semantics

Node indices refer to logical node positions, not raw file columns.

Given the data layout:

#+BEGIN_EXAMPLE
time spin_1 X_1 spin_2 X_2 spin_3 X_3 ...
#+END_EXAMPLE

and the metadata:

#+BEGIN_EXAMPLE
#@ {"type": "node_indexing", "base": 1}
#@ {"type": "node", "index": 1, "name": "CTRL_1"}
#+END_EXAMPLE

the node named ~CTRL_1~ corresponds to:

#+BEGIN_EXAMPLE
spin_1 X_1
#+END_EXAMPLE

not to the first raw column of the file.

With 0-based indexing:

#+BEGIN_EXAMPLE
#@ {"type": "node_indexing", "base": 0}
#@ {"type": "node", "index": 0, "name": "CTRL_1"}
#+END_EXAMPLE

the node named ~CTRL_1~ also corresponds to the first node state in the data
record, i.e.:

#+BEGIN_EXAMPLE
spin_1 X_1
#+END_EXAMPLE

The indexing base affects metadata indices, not the physical order of fields in
the numeric data record.

* Duplicate Metadata Records

If multiple metadata records assign the same field for the same entity, the
later record should override the earlier one.

Example:

#+BEGIN_EXAMPLE
#@ {"type": "node", "index": 5, "name": "pass_a"}
#@ {"type": "node", "index": 5, "name": "pass_A_corrected"}
#+END_EXAMPLE

The effective name of node 5 is:

#+BEGIN_EXAMPLE
pass_A_corrected
#+END_EXAMPLE

Parsers may emit a warning when duplicate assignments are encountered.

This "last record wins" rule allows metadata corrections to be appended without
rewriting the full file.

* Metadata Placement

Metadata records should preferably appear before data records.

Recommended layout:

#+BEGIN_EXAMPLE
#@ {"type": "format", "name": "relaxed-spins", "version": 1}
#@ {"type": "node_indexing", "base": 1}
#@ {"type": "node", "index": 1, "name": "CTRL_1"}

0.000  1 0.12  -1 0.44
0.100  1 0.15  -1 0.43
#+END_EXAMPLE

Metadata records may appear later in the file if an application supports this.

Example:

#+BEGIN_EXAMPLE
0.000  1 0.12  -1 0.44
#@ {"type": "node", "index": 1, "name": "CTRL_1"}
0.100  1 0.15  -1 0.43
#+END_EXAMPLE

Applications that require complete metadata before processing data may:

1. perform a pre-scan of the file;
2. reject late metadata;
3. process data with incomplete metadata and update internal state as metadata
   appears.

For streaming applications, metadata should be interpreted as updates to the
current session state, subject to the restriction that global metadata such as
~node_indexing~ should not change.

* Parser Behavior

A compliant enhanced file parser should:

1. read input line by line;
2. ignore empty lines;
3. ignore ordinary comment lines beginning with ~#~ but not ~#@~;
4. parse lines beginning with ~#@~ as JSON after removing the ~#@~ prefix;
5. require the parsed metadata value to be a JSON object;
6. parse non-comment lines as numeric data records;
7. ignore metadata records with unknown ~type~ values unless in strict mode;
8. ignore unrecognized fields in known records unless in strict mode;
9. apply the global ~node_indexing~ base to all node indices;
10. warn or error on malformed metadata according to parser policy.

Suggested policy for malformed metadata:

- permissive mode: warn and continue;
- strict mode: raise an error.

Suggested policy for duplicate node metadata:

- later records override earlier records;
- parsers may warn.

Suggested policy for conflicting ~node_indexing~ records:

- strict mode: error;
- permissive mode: warn and continue using the first valid global base, or apply
  an implementation-defined policy.

Implementations should document their chosen permissive-mode behavior.

* Minimal File Example

#+BEGIN_EXAMPLE
# Relaxed-spin simulation output.
#@ {"type": "format", "name": "relaxed-spins", "version": 1}
#@ {"type": "node_indexing", "base": 1}
#@ {"type": "node", "index": 1, "name": "CTRL_1"}
#@ {"type": "node", "index": 5, "name": "pass_a"}
#@ {"type": "node", "index": 6, "name": "pass_b"}

0.000  1 0.12  -1 0.44  1 0.91
0.100  1 0.15  -1 0.43  1 0.89
#+END_EXAMPLE

* Stream-Based Format

For stream-based transport, such as a UNIX domain socket, the same JSON objects
may be transmitted directly as NDJSON records without the ~#@~ prefix.

Each stream message is one complete JSON object followed by a newline.

Example stream:

#+BEGIN_SRC json
{"type": "format", "name": "relaxed-spins", "version": 1}
{"type": "node_indexing", "base": 1}
{"type": "node", "index": 1, "name": "CTRL_1"}
{"type": "node", "index": 5, "name": "pass_a"}
{"type": "node", "index": 6, "name": "pass_b"}
{"type": "sample", "time": 0.0, "node_states": [[1, 0.12], [-1, 0.44], [1, 0.91]]}
{"type": "sample", "time": 0.1, "node_states": [[1, 0.15], [-1, 0.43], [1, 0.89]]}
#+END_SRC

The receiver may process each object as soon as the newline is received.

* Stream Sample Records

A stream-native data sample may be represented as:

#+BEGIN_SRC json
{"type": "sample", "time": 0.0, "node_states": [[1, 0.12], [-1, 0.44], [1, 0.91]]}
#+END_SRC

Fields:

- ~type~: must be ~"sample"~;
- ~time~: sample time;
- ~node_states~: array of node states.

Each node state is represented as:

#+BEGIN_SRC json
[spin, X]
#+END_SRC

where:

- ~spin~ is expected to be ~+1~ or ~-1~;
- ~X~ is numeric.

The stream sample:

#+BEGIN_SRC json
{"type": "sample", "time": 0.0, "node_states": [[1, 0.12], [-1, 0.44], [1, 0.91]]}
#+END_SRC

is semantically equivalent to the file data record:

#+BEGIN_EXAMPLE
0.000  1 0.12  -1 0.44  1 0.91
#+END_EXAMPLE

* Bidirectional Control and Feedback Messages

The same NDJSON mechanism may be used for messages sent from a consumer,
frontend, or controller back to the source or backend.

Example pause command:

#+BEGIN_SRC json
{"type": "control", "command": "pause"}
#+END_SRC

Example resume command:

#+BEGIN_SRC json
{"type": "control", "command": "resume"}
#+END_SRC

Example stop command:

#+BEGIN_SRC json
{"type": "control", "command": "stop"}
#+END_SRC

Example parameter update:

#+BEGIN_SRC json
{"type": "control", "command": "set_parameter", "name": "temperature", "value": 0.25}
#+END_SRC

For request-response interactions, messages may include an optional ~id~ field.

Example request:

#+BEGIN_SRC json
{"type": "control", "id": "msg-17", "command": "set_parameter", "name": "temperature", "value": 0.25}
#+END_SRC

Example acknowledgment:

#+BEGIN_SRC json
{"type": "ack", "id": "msg-17", "status": "ok"}
#+END_SRC

Example error response:

#+BEGIN_SRC json
{"type": "error", "id": "msg-17", "message": "Invalid value"}
#+END_SRC

* Recommended Message Types

The following top-level ~type~ values are recommended for the initial version
and likely future extensions:

- ~format~
- ~node_indexing~
- ~node~
- ~created~
- ~title~
- ~notes~
- ~sample~
- ~control~
- ~ack~
- ~error~
- ~warning~
- ~heartbeat~

Example warning:

#+BEGIN_SRC json
{"type": "warning", "message": "Late metadata update for node 5"}
#+END_SRC

Example heartbeat:

#+BEGIN_SRC json
{"type": "heartbeat", "time": "2026-01-26T18:44:00Z"}
#+END_SRC

* Compatibility

This metadata extension is backward-compatible with existing file parsers that
ignore lines beginning with ~#~.

Given the file:

#+BEGIN_EXAMPLE
#@ {"type": "format", "name": "relaxed-spins", "version": 1}
#@ {"type": "node_indexing", "base": 1}
#@ {"type": "node", "index": 1, "name": "CTRL_1"}

0.000  1 0.12  -1 0.44
0.100  1 0.15  -1 0.43
#+END_EXAMPLE

legacy parsers see only:

#+BEGIN_EXAMPLE
0.000  1 0.12  -1 0.44
0.100  1 0.15  -1 0.43
#+END_EXAMPLE

Enhanced parsers may recover the metadata from the ~#@~ records.

* Design Rationale

** Why use comment-prefixed NDJSON in files?

Comment-prefixed NDJSON provides:

- backward compatibility with existing parsers;
- line-oriented parsing;
- simple error recovery;
- standard JSON parsing in Python, Julia, Rust, and other environments;
- a natural transition path to stream-based transport;
- a natural basis for bidirectional control and feedback messages.

** Why use ~node~ instead of ~pair~?

Although the numeric file layout stores each entity as a pair of values,
~spin_i X_i~, the semantic entity is a single relaxed spin assigned to a node.

The term ~node~ describes the semantic entity without tying metadata terminology
to the physical storage layout.

** Why make ~node_indexing~ explicit?

Current workflows may use 1-based indexing, especially in Julia-based tooling.
Future backends and processors may use 0-based indexing.

An explicit global indexing declaration avoids ambiguity:

#+BEGIN_SRC json
{"type": "node_indexing", "base": 1}
#+END_SRC

If absent, the default is 1-based indexing. However, producers should emit the
record explicitly.

** Why is ~node_indexing~ global?

Allowing indexing conventions to change within a file or stream would make node
references ambiguous and error-prone.

Therefore, ~node_indexing~ has global meaning for the file or stream session.
Conflicting declarations should be treated as invalid or at least strongly
discouraged.

* Summary

The recommended file metadata form is:

#+BEGIN_EXAMPLE
#@ {"type": "node", "index": 5, "name": "pass_a"}
#+END_EXAMPLE

The recommended explicit indexing declaration is:

#+BEGIN_EXAMPLE
#@ {"type": "node_indexing", "base": 1}
#+END_EXAMPLE

The corresponding stream message form is the same JSON object without the ~#@~
prefix:

#+BEGIN_SRC json
{"type": "node", "index": 5, "name": "pass_a"}
#+END_SRC

This approach preserves compatibility with existing data files while providing a
clean path toward NDJSON-based streaming, feedback, and control protocols.
